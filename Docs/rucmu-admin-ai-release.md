# RuCMU AI Admin Assistant: запуск, проверка и откат

Актуальная инструкция для ветки `codex/rucmu-admin-ai-safe-faq`, подготовленной
на `flex5hybrid/RussianCM:master` (`02084d038c9`). Документы этапов A–C и локального
WSL описывают исторические проверки; эта инструкция описывает текущую поставку.

## Что поставляется

- Отдельный локальный llama.cpp worker и серверный транспорт только через UDS.
- Приватный черновик в существующем ахелпе. «Вставить» дополняет поле ответа;
  сообщение игроку отправляет администратор обычной кнопкой.
- Локальный индекс опубликованных руководств: медицина, связь, инженерия,
  снабжение, правила и SOP. Штатные подписи GameTicker дают публичное название карты.
- Отдельная вкладка «Контекст» для `Adminhelp + Logs`: ручной ограниченный запрос
  журнала и отчёт с реальными `roundId:logId`, временем UTC и выдержками.
- Отдельно включаемые SafeFAQ и один нейтральный уточняющий вопрос на обращение,
  когда отсутствует любой подключённый администратор, включая скрытого или AFK.
- Ограниченная очередь, тайм-ауты, отмена, защита по PSI/границам игровых тиков,
  диагностика `admin_ai_status`, журнал действий без текстов обращений.

Модель генерирует только приватный черновик. Быстрые публичные ответы — выдержки
из реальных источников; уточнения — фиксированный нейтральный текст. Отчёт по
журналу строится программно из фактической выборки: модель не создаёт доказательства,
время или номера записей. Семантическое установление мотивов/виновности остаётся
администратору. Заметки администрации не читаются. Привилегированные внутренние
инструкции не импортируются; новые источники должны проходить отдельный аудит доступа.

## Установка на Linux

CPU-модель с подтверждённым правильным ответом за 3 секунды ещё не выбрана.
Проверенные маленькие модели не прошли приёмку качества; прежний GPU smoke
также не гарантирует качество произвольного диалога. Перед включением генерации
нужна проверка ответов и нагрузки. История теперь передаётся отдельными репликами;
пределы хранения и результаты изложены в [CPU-протоколе](rucmu-admin-ai-cpu-context.md).

1. Собрать обычные сервер и клиент из этой ветки с соответствующим ей неизменённым
   RobustToolbox. Сервер и клиент нужно обновить вместе: добавлены сетевые сообщения.
   Модель и llama-server в сборку игры не входят; запуск ничего не скачивает.
2. На целевом хосте выполнить `deploy/linux/audit-game-placement.sh`, передав
   реальные имена RuCMU и всех трёх Squad service. Сохранить исходные tick/TPS,
   p95/p99, PSI, RAM, CPU affinity/NUMA и IO. Шаблон не угадывает свободные ядра.
3. Подготовить локальные лицензированные артефакты llama-server/GGUF и файл лицензии.
   Зафиксировать версию и SHA256 в root-owned `/etc/rucmu-ai/worker.env` по
   `deploy/linux/worker.env.example`. Проверенные локальные артефакты и лицензия
   перечислены в [отчёте WSL](rucmu-admin-ai-local-wsl.md).
4. Создать отдельного пользователя `rucmu-ai` и группу `rucmu-ai-socket`. Поместить
   бинарник и `worker-preflight.sh` в `/opt/rucmu-ai/bin`, модель — в `/opt/rucmu-ai/models`.
   Всё root-owned, без права записи worker. Добавить пользователя игрового сервера
   в группу сокета; перезапустить его с новой группой.
5. Установить `rucmu-ai-worker.service`. Проверить шаблон на целевой версии systemd,
   локальную доступность UDS и реальные cgroup-лимиты. Запустить worker отдельно
   от игры. Префлайт проверяет артефакты/версии; TCP и облачного fallback нет.
6. Добавить настройки из `admin-ai.toml.example`. `cgroup_paths` должен содержать
   четыре проверенных абсолютных пути cgroup, разделённых `;`. Сначала включить
   только `enabled=true`, проверить Normal/Ready и ручной черновик. Затем отдельно
   разрешить `investigation`, `safe_faq`, `clarification` согласно политике сервера.

Worker: CPUQuota 100%, один поток инференса и подготовки, CPU/IO weight 1, Nice 15,
MemoryHigh 3 GiB, MemoryMax 4 GiB, swap 0, один контекст и одна генерация. Два потока
под квотой одного CPU уже вызывали лишнюю CPU pressure в WSL; шаблон это учитывает.
CPU affinity задаётся только по результату проверки четырёх игровых служб.

Нужны Linux, UDS, PSI и cgroup v2 для штатной защищённой эксплуатации. Для Windows
используется локальная WSL2: [инструкция](rucmu-admin-ai-local-wsl.md). Sandbox,
engine API, версии подмодулей и настройки VPN/firewall не ослабляются.

## Ограничения контекста и доступа

Вкладка контекста прокручивается в ограниченной области, сохраняя место для обычного
ахелпа и поля отправки. При вытеснении кейса очищается только его прежняя выборка.

Контекст относится к выбранному актуальному обращению текущего раунда. Раунд
берётся с сервера и передаётся клиентом для проверки совпадения; исторические раунды
и произвольное время не доступны через этот интерфейс. Окно по умолчанию 5 минут
до последнего сообщения игрока и 2 после, общий максимум 15 минут, допустимый CVar
предел до 30. UI позволяет выбрать автора и ещё одного участника из списка;
серверный протокол допускает максимум четырёх участников, всегда включая автора.

По умолчанию до 64 записей и 24000 символов всего, до 512 символов на запись.
Тексты — ограниченные выдержки, а не полная выгрузка журнала. Один физический запрос
БД, тайм-аут 5 секунд. Backend, игнорирующий cancellation, продолжает занимать слот;
новые запросы не накладываются на него. Отчёт автоматически удаляется через TTL.
Нет записи в журнале — недостаточно данных, а не доказательство отсутствия события.

Проверки owner/session/view/case/revision/round/epoch и прав повторяются при выдаче.
Смена обращения, новое сообщение, потеря прав, переподключение, reload конфигурации
или раунда отменяют старый результат. Отчёт и сами логи нельзя вставить кнопкой
черновика в сообщение игроку. Отсутствие `Logs` исключает содержание журнала.

Все автоматические режимы по умолчанию выключены. SafeFAQ не отвечает на жалобы,
санкции, неизвестные свойства предметов и запросы закрытых данных. Он требует
Normal/Ready и публичного источника. Уточнение не принимает решения и не закрывает
обращение. Ни один режим не вызывает административные наказания или команды.

## Скорость и воспроизводимость

Дополнение 2026-10-14: для локального WSL проверена настоящая GPU-генерация
кратких черновиков до 20 слов. Итоговый q8/512 с двумя клиентами: две серии
по 30/30 Success, p95 0,60/0,62 s, максимум 0,61/0,66 s. Ещё 30/30 с входом
3975 символов: p95 0,69 s, max 0,80 s. Это модель + UDS, без времени игровой
очереди/сети/UI; полный ручной E2E нового профиля ещё не подтверждён. Предыдущий
FP16-профиль при конкурирующей нагрузке доходил до timeout; отрицательный
результат и разные условия сохранены, универсальная гарантия 3 s не заявляется.
Приветствия не подменяются посторонними справочниками. Отдельный GPU-профиль,
точные условия, первые медленные варианты и ограничения описаны в
[протоколе GPU](rucmu-admin-ai-gpu-wsl.md). CPU-профиль не объявляется способным
генерировать любые ответы за 3 секунды.

На фиксированном корпусе 259 документов / 5728 фрагментов проведено по 100 прогревочных
и 3000 измеряемых запросов для прежнего и нового кода, в одной сборке Release:

| Поиск | Прежний p95 | Новый p95 | Новый p99 |
| --- | ---: | ---: | ---: |
| Три типовых вопроса по механике | 0,1181 мс | 0,0179 мс | 0,0229 мс |
| Полнотекстовый поиск | 0,7025 мс | 0,0165 мс | 0,0190 мс |

Это время lookup в готовом индексе, без сети, очереди и модели. Построение индекса
однократное и фоновое; используются postings и отдельный индекс документов,
без общего кэша переписок. Полнотекстовый запрос выделяет около 5032 bytes против
4349 раньше; ускорение CPU оплачено небольшим увеличением временных выделений.
Кнопки источников клиент больше не перестраивает при каждом одинаковом статусе.
Переключение автоматических режимов не перезапускает инфраструктуру/governor.

Worker использует ограниченные prefill-буферы `batch/ubatch=128` и q8 KV-кеш при
контексте 4096. На закреплённой модели это снизило наблюдаемую память после запроса
с 3,22 до 2,42 GB, без увеличения лимитов CPU/RAM. В итоговом smoke счётчики
`memory.high/max/oom/oom_kill` оставались нулевыми. Поддержку этих параметров другой
сборкой llama.cpp необходимо проверить до установки; скрытого fallback нет.

Настоящая модель через production UDS-клиент: Ready / Success, 12,07 секунды на первом
запросе после перезапуска и 4,89 секунды на прогретом worker. Это отдельные замеры
фиксированного синтетического prompt, не p95 обычных обращений. До настройки памяти
после перезапуска измерено 24,79 секунды с ростом `memory.high`; прежний прогретый
замер — 3,57 секунды. Сложный черновик может достигать 45-секундного тайм-аута.
Самые частые вопросы и публичная карта обходятся без модельной генерации.

## Проверка перед включением

Локальные focused runners:

```powershell
dotnet Tools/AdminAI.Tests/bin/Debug/net10.0/AdminAI.Tests.dll boundary
$env:RUCMU_AI_TEST_SOCKET = Join-Path $env:TEMP ('rucmu-ai-' + [guid]::NewGuid().ToString('N').Substring(0,8) + '.sock')
dotnet Tools/AdminAI.Tests/bin/Debug/net10.0/AdminAI.Tests.dll ipc
$env:RUCMU_AI_ENGINE_RESOURCES = Join-Path $PWD 'RobustToolbox/Resources'
$env:RUCMU_AI_CONTENT_RESOURCES = Join-Path $PWD 'Content.CMU/Resources'
dotnet Tools/AdminAI.ServerTests/bin/Debug/net10.0/Content.IntegrationTests.dll ipc
dotnet Tools/AdminAI.ClientTests/bin/Debug/net10.0/Content.IntegrationTests.dll ipc
```

Сначала собрать Tools-проекты с путями к своим соответствующим платформе content
и engine DLL. ClientTests нужны native-библиотеки из `runtimes/win-x64/native`,
а не весь каталог Content.Client: старые игровые DLL нельзя копировать поверх новых.
Linux ServerTests использует отдельную Linux-сборку. Обычный CI не должен запускать
локальный UI fixture без его явно заданных resource paths; pure-тесты находят корень
checkout независимо от рабочего каталога runner.

Актуальные числа и команды сборок приведены в [протоколе проверки](rucmu-admin-ai-release-validation.md).
Журналы и NUnit XML находятся в ignored `.codex-build/admin-ai/release-*`; модель,
бинарники, БД, обращения игроков и локальные настройки не включаются в Git.

Для ручной эксплуатационной приёмки проверить два клиента: четыре типовых вопроса
без администрации, появление администратора во время запроса, неизвестный вопрос,
жалобу и её единственное уточнение, приватный отчёт, снятие `Logs`, отмену,
смену раунда и выключенный worker. Ручная отправка черновика ранее подтверждена
пользователем. Новые автоматические ответы и отчёт проверены через compiled handlers
и headless UI fixtures; полного сетевого E2E этих новых режимов пока нет.

Production-приёмка RuCMU + трёх Squad остаётся обязательной перед включением:
реальный хост, четыре service/cgroup и нагрузка не предоставлены. Нельзя считать
локальные замеры доказательством отсутствия влияния на эти серверы.

## Откат

Сначала установить `cmu.admin_ai.enabled=false`: новые запросы прекращаются,
очередь отменяется, приватные виды очищаются, штатный ахелп продолжает работать.
Затем оператор отдельно останавливает `rucmu-ai-worker.service`; игра не управляет
службой. Если требуется откат к старой версии, вернуть совместимые сервер и клиент
одновременно. Миграций БД, изменений сохранений и зависимостей движка нет.
