# Контекст ахелпа и CPU-модели: проверка 2026-10-15

## Что исправлено

В прежнем ручном черновике история передавалась одной строкой с пределом 800
символов. Поиск справочника использовал только последнюю реплику игрока.
Продолжение «Я не знаю, я новичок» теряло медицинскую тему; готовый справочный
ответ мог обходить генерацию даже при наличии переписки.

Теперь модель получает отдельные роли `user`/`assistant` для принятых публичных
сообщений игрока и администратора. При вытеснении сохраняются начало обращения
и последние реплики. Бюджет истории ручного черновика — до 1200 символов;
история и источники вместе ограничены 2300 символами или меньшим действующим
лимитом governor. Общий размер учитывается также при приёме в очередь и в
режиме Degraded. История неизменяема после постановки запроса в очередь.

Поиск для коротких продолжений использует последний сохранённый информационный
вопрос игрока. Это ограниченный словарь продолжений, не полноценное понимание
произвольного диалога. Новый самостоятельный вопрос имеет приоритет; неизвестная
механика не получает случайный источник из лора. Вопрос новичка после вопроса
о лечении получает опубликованный шаг осмотра, без угадывания травмы.

Пределы хранилища сохранены: до 8 сообщений по 512 символов по умолчанию,
до 128 обращений; контекст удаляется через 300 секунд без активности, при смене
раунда или отключении системы. Это память текущего обращения, а не постоянный
архив. Закрытые сообщения администрации не включаются. Проверки владельца,
прав, выбранного обращения и ревизии после генерации сохранены.

Для одиночных разрешённых справочных вопросов и публичного имени карты остаётся
прежняя выдача фактов. Многошаговый ручной черновик использует модель. Политика
автоответов SafeFAQ не расширена: произвольная генерация игроку не отправляется.
Ручной черновик требует проверки и отправки администратором.

## Условия CPU-экспериментов

- Локальный i7-12700F, WSL Ubuntu, оптимизированный backend
  `libggml-cpu-alderlake.so`; llama.cpp b11429 (`d81235049`).
- Отдельный вручную запускаемый test worker и `/run/rucmu-ai/cpu-test.sock`.
  GPU offload = 0, KV offload выключен, контекст 4096, parallel = 1,
  batch/ubatch = 128, FP16 KV, polling выключен.
- Первые 0.6B/0.8B проверки: 1 поток и CPUQuota 100%. Проверки 1.5B/1.7B:
  2 потока и CPUQuota 200%, в пределах первоначального максимума ТЗ.
  CPU affinity не угадывалась. Nice 15, CPUWeight/IOWeight 1, RAM high/max
  3/4 GiB, swap 0, только AF_UNIX, PrivateNetwork/PrivateDevices включены.
- Артефакты скачаны вручную оператором по разрешению пользователя, SHA256 и
  лицензии проверены; игра и worker ничего не скачивают при запуске/инференсе.
  Ни API облачной модели, ни внешнего инференса нет.
- Синтетические случаи: приветствие, новичок после вопроса о лечении,
  продолжение вопроса о радио, смена лечения на радио, уточнение «Это ожог»,
  неизвестная механика, продолжение жалобы после вопроса о времени/месте.
  Полные ответы проверялись по смыслу; HTTP Success не означает правильный ответ.
- Время включает UDS и модель, но не игровую очередь, handler, сеть и UI.
  Между экспериментами менялись и формат истории/инструкции/источники: это
  поиск подходящей конфигурации, а не чистое сравнение только размеров модели.

Последний прогон с `.7/.8/20/0` sampling был экспериментом. В поставке сохранена
прежняя temperature .2; экспериментальные sampling-параметры не продвигаются как
оптимизация. Никакая из CPU-моделей не включена вместо рабочего игрового worker.
Отдельный CPU-test остановлен. При его перезапусках обнаружена очистка общей
systemd RuntimeDirectory, удалявшая имя сокета другого тестового worker:
GPU-worker перезапущен и его сокет восстановлен. Эти два тестовых unit нельзя
эксплуатировать параллельно с общей управляемой runtime-папкой.

**Нет подтверждённой модели, которая одновременно правильно ведёт эти диалоги
и завершает каждый ответ за 3 секунды на выделенных 1–2 CPU.** Снижение размера
модели не исправляет её семантические ошибки. Дообучение в этом изменении не
выполнялось; новый собственный набор весов не создавался. Для следующей проверки
нужен отдельный проверенный набор игровых диалогов с ответами из актуального
справочника и независимые от обучения примеры. Личные ахелпы автоматически
в обучающие данные не экспортируются.

Меньшая модель, дообучение или другой CPU требуют той же приёмки: правильный
ответ, полный `finish_reason=stop`, отсутствие выдуманных фактов, замеры
на худших допустимых длинах и совместная нагрузка RuCMU + трёх Squad. Проверка
пустого локального раунда такую приёмку не заменяет. Универсальная гарантия 3 s
и готовность к релизу не заявляются.

## Воспроизводимая проверка

`Tools/AdminAI.DialogueBench` связывает настоящий код store/retrieval/protocol/UDS.
Никакого mock-инференса, скачивания или изменения служб в нём нет. Он использует
только фиксированные синтетические сообщения и опубликованный allowlist
справочника. Reader прототипов — диагностический, для простых текущих `id/text`
объявлений; игра продолжает использовать штатный prototype loader.

Собрать из корня репозитория, затем запустить на Linux с уже подготовленным
worker и доступом к его сокету:

```text
dotnet build Tools/AdminAI.DialogueBench/AdminAI.DialogueBench.csproj -c Release
dotnet Tools/AdminAI.DialogueBench/bin/Release/net10.0/AdminAI.DialogueBench.dll /path/to/RussianCM /run/rucmu-ai/llama.sock 3 > dialogue.jsonl
```

Вывод: health, 21 полная синтетическая генерация, размер входа/истории,
guide IDs, статус, время и текст, затем p95/max. При недоступном worker код 2;
при неполных ответах или превышении 3 s код 1. Код 0 подтверждает лишь
транспорт и время. Поле `semanticAcceptance=manual-review-required` означает,
что готовность модели вручную оценивается по всем ответам, а не по ключевым словам.
Состояние GPU offload и CPU/RAM/cgroup необходимо проверять отдельно: клиент
не может определить, на каком устройстве считает worker.

Нужно проверить: новичку объяснён опубликованный осмотр; радио соответствует
гарнитуре/`:h`, новая тема заменила лечение; ожог не подменён неизвестной травмой;
неизвестная механика вызывает уточнение без придуманных фактов; жалоба продолжает
сбор деталей и не повторяет уже полученные время/место. Шаблонные ответы,
отрывки справочника и timeout не засчитываются как настоящая генерация.

Для приёмки это лишь короткий smoke. Отдельно нужны максимальный вход, холодный
старт, очереди, длительная нагрузка и ручная проверка F1 с обычным игровым клиентом.
