# Чейнджлог RussianCM

Добавляйте изменения для игроков в блок `:cl:` или `🆑` описания PR. После маркера можно указать имя автора. По умолчанию используется логин автора PR. Поддерживаются типы `add`, `remove`, `tweak`, `fix`, `map`, `code` и `admin`. Русский, английский и смешанный текст попадает в игру и Discord в исходном виде. Пустые блоки, HTML-комментарии и примеры из шаблона пропускаются.

## Сборка

1. `Tools/update_changelog_parts.py` читает объединённые PR через GitHub Pull Requests API и пишет их записи в `Resources/Changelog/Parts`. Поиск идёт по ветке назначения и времени слияния. Повторная проверка семи дней и сверка URL во всех разделах защищают от пропусков при пагинации и дублей при повторных запусках. `start_date` расширяет окно поиска для ручного восстановления.
2. `Tools/update_changelog.py --all` объединяет части с YAML из текущей ветки. Из upstream используются YAML и части, вошедшие в слияние. Повторный PR определяется полным URL с именем репозитория. Сборка восстанавливает ID из предыдущего коммита бота, сохраняет локальные записи при замене файла upstream и выделяет новые ID при коллизиях. Локальная сборка сохраняет старые записи для восстановления доставки.
3. Клиент загружает корневые YAML из `Resources/Changelog` и отображает все шесть разделов. Видимость вкладки Admin зависит от прав пользователя. Счётчик непрочитанного использует ID основного раздела CMU.

| Категория | Итоговый файл | Метка PR |
| --- | --- | --- |
| CMU | `CMU.yml` | `Changelog: CMU` |
| RMC14 | `RMC14.yml` | `Changelog: RMC14` |
| Main | `Changelog.yml` | `Changelog: Main` |
| Maps | `Maps.yml` | `Changelog: Maps` |
| Admin | `Admin.yml` | `Changelog: Admin` |
| Rules | `Rules.yml` | `Changelog: Rules` |

Указывайте одну метку категории. Без неё локальный PR попадает в CMU или в категорию, выбранную в ручном запуске. Категория upstream-части задаётся полем `category` в YAML. Часть без поля относится к CMU. Тип изменения определяет значок строки и может использоваться в любой категории.

При конфликте upstream merge объедините записи обеих сторон по полному URL и сохраните локальные ID. Если upstream заменяет файл целиком, бот восстанавливает локальные записи из предыдущего коммита. Смысловые исправления и откаты должны отражаться в исходном changelog.

## Автоматизация и выпуск

**Changelog** запускается при push в `master`, ежедневно в 13:00 по Москве и вручную. Production-коммит и Discord разрешены только на основной ветке. Переменная `DONT_UPDATE_CHANGELOG=true` приостанавливает автоматические запуски, ручной предпросмотр остаётся доступен. При конкурентном push сборка повторяет попытку на новом состоянии ветки. Коммит бота создаётся через стандартный `GITHUB_TOKEN`, поэтому его push не запускает новый workflow.

При включённом `use_changelog` **Publish** и **Fast Publish** ждут сборку changelog. Один SHA используется для упаковки и для начала, загрузки и завершения публикации на CDN. Задание Discord выполняется отдельно и запускается также после завершения релизного workflow на основной ветке. Оно проверяет последний собранный YAML даже при отсутствии нового коммита changelog.

## Discord и журнал доставки

Публикация использует `CHANGELOG_DISCORD_WEBHOOK` и `GITHUB_TOKEN`. Сообщения содержат раздел, автора, дату, типы изменений и ссылку на PR. Каждый фрагмент укладывается в 2 000 единиц UTF-16. Упоминания выключены, ответ HTTP 429 обрабатывается с ограниченным ожиданием.

Журнал `discord-delivery.json` хранится в ветке `codex/changelog-discord-state`. Подтверждения определяются разделом и URL PR. Для записей без URL используются автор, нормализованная дата и содержимое. У более ранней даты upstream нет влияния на доставку новой записи. Историческая база исключает записи из обычной очереди и сама по себе ничего не подтверждает.

Версия 2 убирает старый кеш перевода при очередной записи журнала. Ключи исторической базы, подтверждения и сохранённая очередь переносятся без изменений. Если старый запуск уже подготовил сообщения, очередь сохраняет их исходные для этой очереди байты, квитанции и позицию. Новая очередь формируется из YAML.

Перед запросом бот сохраняет позицию `in_flight`, а после ответа с ID сообщения записывает квитанцию. После явного отказа повторный запуск продолжает с первой неподтверждённой части. Если Discord мог принять сообщение, откройте канал и запустите **Changelog** с `dry_run=false` и нужным `delivery_resolution`:

- `delivered`, если спорное сообщение есть в канале.
- `retry`, если спорного сообщения в канале нет.

При повреждённом журнале или исчезновении файла из существующей служебной ветки workflow останавливается. Сохраняйте служебную ветку отдельно от `master`.

## Предпросмотр и восстановление

1. В **Actions → Changelog → Run workflow** оставьте `dry_run=true`. Можно указать `start_date` в UTC, например `2026-10-31`. Артефакт `discord-changelog-preview` содержит остаток сохранённой очереди и записи, найденные при сборке. Предпросмотр не отправляет сообщения и не меняет Git или журнал.
2. Сверьте предпросмотр с Discord. `start_date` повторно проверяет локальные PR и включает исторические записи с указанной даты. Ключи из `delivered` остаются исключёнными. Записи, исчезнувшие из файлов до этой версии, можно восстановить из git или исходных PR.
3. Для запуска восстановления используйте те же параметры с `dry_run=false` на `master`. После первого запуска без журнала историческая база охватывает всё до даты восстановления или до начала последних 30 дней. При существующем журнале сохраняются его границы и подтверждения.

Локальный предпросмотр по снимку журнала:

```bash
git show origin/codex/changelog-discord-state:discord-delivery.json > /tmp/discord-delivery.json
python Tools/actions_changelogs_since_last_run.py --dry-run \
  --state-file /tmp/discord-delivery.json --output /tmp/discord-preview.md
```
