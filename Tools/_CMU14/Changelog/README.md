# Чейнджлоги и русский Discord

Цепочка состоит из трёх независимых шагов:

1. `update_changelog_parts.py` читает `:cl:` у PR, влитых в текущую ветку **этого репозитория**. Даты апстримных записей не сдвигают локальный курсор. Имена частей включают отпечаток полного URL, поэтому одинаковые номера PR разных репозиториев не конфликтуют.
2. `update_changelog.py --all` собирает CMU, RMC14, Main → Changelog, Maps, Admin и Rules. Без категории часть относится к выбранной категории, обычно CMU. Сборщик сохраняет идентификаторы, объединяет дубликаты URL, исправляет коллизии идентификаторов и удаляет части только после записи результата. В исходных YAML сохраняется исходный язык.
3. `actions_changelogs_since_last_run.py` читает все шесть файлов **из текущего checkout**, переводит выбранные записи на русский и сверяется с отдельным журналом доставки. Не загружает текущий HEAD внешних апстримов: изменения должны сначала попасть в вашу ветку.

Записи апстрима, уже находящиеся в YAML после слияния, проверяются даже когда сборщик ничего не изменил. После первого запуска новая запись с давней апстримной датой тоже считается новой. В качестве ключа используется раздел и полный URL PR; ID, автор и представление даты у PR не влияют на повторную доставку. Ручные записи без URL определяются автором, нормализованной датой и содержимым; при отсутствии даты используются автор и содержимое.

Автоматика запускается ежедневно и при изменении `Resources/Changelog` в master. Publish и Fast Publish используют тот же workflow при включённом `use_changelog`. Отправка и автоматический коммит разрешены только для default branch; другие ветки работают как предпросмотр. Группа concurrency объединяет эти запуски. Непосредственный запуск Python вне workflow нельзя выполнять одновременно с production workflow.

## Перевод

Для Discord используется Mistral Chat Completions с JSON-ответом. В репозитории уже есть секрет с именем `MISTRAL_API_KEY`; его работоспособность необходимо проверить первым предпросмотром в Actions. Параметр репозитория `CHANGELOG_TRANSLATION_MODEL` переопределяет модель, по умолчанию `mistral-small-latest`.

`Tools/_CMU14/Changelog/changelog-russian.yml` содержит терминологию, сохраняемые обозначения и точные редакторские замены (`overrides`: исходная строка → русский перевод). Числа, проценты, ссылки, текст в обратных кавычках и перечисленные обозначения защищены маркерами. Проверяется количество ответов, соответствие их ID, сохранность маркеров, наличие русского текста и отсутствие оставленных английских предложений. Смешанный русский/английский текст тоже проходит перевод.

Успешные переводы кешируются отдельно от доставки и, при реальной отправке, также в журнале. Проверенные пакеты сохраняются сразу после перевода, а не только в конце всей очереди. Предпросмотр пишет только отдельный кеш переводов `.tmp/changelog-translation-cache.json`: журнал доставки остаётся неизменным. Actions восстанавливает этот кеш и сохраняет его даже после ошибки, поэтому повторный запуск с той же датой подхватывает выполненную работу. Кеши GitHub имеют область видимости ветки: предпросмотр в отдельной ветке не гарантирует доступность его кеша из master. Изменение глоссария или редакторских замен меняет ключ кеша. Уже доставленные записи из-за этого повторно не отправляются. Если перевод отсутствует или не проходит проверку, workflow падает, а записи остаются недоставленными. Английского fallback нет.

Автоматическая проверка не доказывает идеальную смысловую точность перевода. Для важных изменений баланса и правил следует посмотреть предпросмотр и при необходимости добавить редакторскую замену. Исходные YAML остаются совместимыми с апстримом; этот механизм переводит Discord, а не окно чейнджлога в клиенте.

### Если Mistral вернул HTTP 429

Для короткой проверки доступа выбрать Actions → Changelog → Run workflow, включить `diagnose_only=true`. Выполнится отдельный job `diagnose`: чтение каталога моделей и один запрос с фиксированным текстом и `max_tokens=32`. Он не читает чейнджлоги, не получает Discord webhook, не пишет журнал, не собирает и не коммитит YAML. Параметры даты и публикации при такой проверке не используются. Отказ даже этого маленького запроса указывает, что одного уменьшения пакета недостаточно; нужно проверить модель, аккаунт и workspace.

Диагностика показывает только числовые заголовки лимитов, известные категории и коды ошибок. Тексты ответа провайдера, ключи и произвольные заголовки не выводятся. Если Mistral сообщает нулевой **полный лимит** запросов или токенов, основной перевод останавливается сразу с указанием API/Limits. Нулевой **остаток** минутного лимита остаётся временным ограничением и обрабатывается ожиданием.

Запросы идут последовательно, пакет ограничен шестью строками и примерно 1600 символами. Явно ограничивается `max_tokens`, чтобы короткий перевод не резервировал неоправданно большой ответ. Между запросами выдерживается 15 секунд; изменить интервал можно переменной репозитория `CHANGELOG_TRANSLATION_INTERVAL_SECONDS` (минимум 1 секунда).

Для 429 учитывается `Retry-After` в секундах или формате HTTP-даты. Если заголовка нет, ожидание начинается с 60 секунд, растёт до 180 секунд; до шести попыток и максимум десять минут на текущий пакет. Серверное ожидание, превышающее бюджет, не сокращается до преждевременного повтора — процесс останавливается с пояснением. Вся фаза перевода ограничена примерно 18 минутами, чтобы успеть сохранить кеш до таймаута job. Прогресс переводов выводится по пакетам без публикации исходных текстов и секретов.

429 может означать запросы/токены в минуту либо исчерпанный бюджет/месячную квоту workspace. При явном сообщении провайдера о месячной квоте или оплате повторные запросы не выполняются. Проверить **Mistral Admin Panel → API → Limits** и **Subscriptions → Billing**. После восстановления лимита повторить тот же запуск с той же датой: кешированные переводы будут использованы снова. Смена `category` или дробление даты не восстанавливают исчерпанный бюджет аккаунта. Диагностика не выводит сырой ответ сервиса или API-ключ.

[Mistral: лимиты API](https://docs.mistral.ai/admin/billing-usage/usage-limits), [лимиты workspace и HTTP 429](https://docs.mistral.ai/getting-started/quickstarts/admin/manage-workspaces).

## Журнал доставки

Состояние находится в `discord-delivery.json` отдельной ветки `codex/changelog-discord-state`. Workflow создаёт её при первой реальной отправке через GitHub API, используя стандартный `GITHUB_TOKEN` с `contents: write`. Журнал содержит историческую базу, подтверждённые записи, кеш переводов и подготовленную очередь. Не сливать эту ветку в master и не удалять журнал: он хранит подтверждения доставки независимо от истории Actions и слияний апстрима.

Перед отправкой сохраняется весь русский пакет сообщений. Каждое сообщение укладывается в 2000 единиц UTF-16; длинные изменения разбиваются без потери текста, со ссылкой на PR на каждой части. Упоминания выключены. Discord вызывается с `wait=true`, и подтверждение с ID сообщения сохраняется после каждой части. HTTP 429 обрабатывается ограниченным повтором с `retry_after`.

При явном отказе Discord следующий запуск продолжает с неподтверждённой части. При обрыве связи, аварийной остановке или ошибке сохранения квитанции невозможно автоматически определить, успел ли Discord принять последнее сообщение. В этом случае журнал оставляет запрос в состоянии `in_flight`, дальнейшая отправка останавливается. Проверить канал и запустить workflow с `dry_run=false`, выбрав `delivery_resolution`:

- `delivered` — спорное сообщение уже есть в канале; продолжить со следующего.
- `retry` — спорного сообщения нет; повторить эту часть.
- `none` — обычный режим.

Предпросмотр не меняет это состояние. При повреждённом или пропавшем журнале на существующей служебной ветке отправка тоже останавливается; история не сбрасывается автоматически. Смена канала/вебхука не означает повторную публикацию старых записей: журнал обслуживает одну ленту этого репозитория.

## Первый запуск и восстановление

В Actions открыть **Changelog → Run workflow**. По умолчанию `dry_run=true`: собирается свежий результат и прикладывается `discord-changelog-preview`, без коммита, отправки или изменения журнала. Перевод при этом может обращаться к Mistral.

При отсутствии журнала стандартное окно восстановления составляет **последние 30 дней** относительно запуска. Всё более старое становится исторической базой. Доставки старой автоматики не импортируются: первый запуск может повторить уже опубликованные сообщения внутри выбранного окна. Поэтому для первого запуска следует задать `start_date` по фактическому последнему сообщению в канале и сначала посмотреть предпросмотр. Успешный старый workflow мог иметь пропущенную задачу Discord и не доказывает доставку.

После проверки запустить с теми же параметрами и `dry_run=false`. Для восстановления более старого периода указать `start_date`, например `2026-09-20T00:00:00Z`. Дата открывает историческую базу с указанного момента и используется при поиске локальных PR. Записи, подтверждённые новым журналом, повторно не отправляются. Не нужно менять ID или YAML вручную.

Уже поставленная в очередь доставка завершается первой; изменение даты не меняет её подготовленный текст. Старые записи, уже удалённые из файлов из-за лимита хранения, восстановить одним `start_date` нельзя. Их надо отдельно вернуть из нужного исторического диапазона, сохранив URL и проверив актуальность изменений. PR без непустого `:cl:` автоматически не превращается в описание коммитов. При отмене/откате апстрима сам источник чейнджлога также должен отражать отмену: сборщик не выводит смысл отката из кода.

Для локального предпросмотра с установленными requests и PyYAML:

```powershell
python Tools/actions_changelogs_since_last_run.py --dry-run --state-file .tmp/discord-journal.json --translation-cache .tmp/changelog-translation-cache.json --start-date 2026-09-20 --output .tmp/discord-preview.md
```

Без файла журнала локальный предпросмотр начинает новую базу. Для просмотра production-состояния использовать Actions; не запускать локальную отправку с отдельным журналом в рабочий канал.

## Проверки и защита от регрессий

```powershell
python -m unittest discover -s Tools/_CMU14/Changelog -p "test_changelog*.py"
```

Проверки работают без секретов и настоящих сетевых вызовов. Они покрывают поломку сборщика после merge, все категории, коллизии PR и ID, дубликаты, pruning, старые/отсутствующие даты, восстановление, кеш и ошибки перевода, лимиты Discord, подтверждения, частичный сбой, неоднозначную отправку и отсутствие побочных эффектов предпросмотра. Отдельный workflow **Changelog tools** запускает их на PR и push, а production workflow — перед сборкой.

Подтверждённая исходная поломка: [запуск 5 октября 2026](https://github.com/flex5hybrid/RussianCM/actions/runs/37361121935) упал с `UnboundLocalError` на `raw`. В [успешном запуске 19 сентября](https://github.com/flex5hybrid/RussianCM/actions/runs/35446709866) Discord job был skipped. Поэтому сравнение с родителем последнего auto-commit или просто статусом успешного запуска не годилось как журнал доставки.

Описание API: [Mistral JSON mode](https://docs.mistral.ai/studio/conversations/structured-output/json_mode), [Discord Execute Webhook](https://docs.discord.com/developers/resources/webhook#execute-webhook), [GitHub Contents API](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents).
